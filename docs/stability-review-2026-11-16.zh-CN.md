# 稳定性、用户控制与自动化审查

审查日期：2026-11-16。基于 `853c8a05d087166ac5c2181bd173ba4a2bd7f407`。
优先顺序：稳定性第一，随后扩大用户选择与自动化能力。

初次审查进行了源码审查、现有回归、隔离故障复现和真实固定版本引擎验证。
审查阶段未修改业务代码或覆盖安装手机，也未调用真实服务商或付费模型。下方保留原始发现，修复情况见文末。
P1 表示应优先修复的执行可靠性或发布阻塞；P2 表示有条件触发的问题与工作流缺口。

## 已确认问题

### 1. [P1] 多工具响应部分损坏时，已发出的命令会被重试执行

位置：`gateway/gw/codex-chat-adapter.mjs:145`；相关重试配置：`gateway/gw/codex-connection.mjs:100`。

适配器在同一个循环里校验并发布每个工具调用。第一条合法调用的
`response.output_item.done` 已交给引擎执行后，第二条调用若含有损坏的 JSON，
适配器才报错并关闭流，最终没有 `response.completed`。引擎随后重试整个请求。

真实 `codex-app-server 0.166.0` 配合回环 Chat 接口复现：提供一个合法的临时文件
追加命令和一个无效工具参数，服务收到 2 次请求，临时文件追加 2 次，最终任务失败。
测试使用 `approvalPolicy: never` 来独立验证执行行为，未访问用户项目；产品中的
受信命令、已有任务授权，以及以后开放的无人值守模式也需要处理此问题。

修复方向：先校验整批工具，再发布任何可执行事件；对已产生工具副作用后的流失败，
必须核实引擎重试和调用去重的语义，不能把普通请求重试直接当成可靠的任务恢复。
验收需要同时断言执行次数和任务结果，覆盖第二条无效调用、截断、断网与重试。

### 2. [P1] 项目路径失效后静默切换工作目录

位置：`gateway/gw/codex.mjs:661`。

`startThread(cwd)` 对显式指定但已经不存在的目录，也采用默认工作区回退。
项目被重命名、删除或存储暂时不可用时，新任务会继续创建于另一个位置。
隔离复现确认：传入不存在的项目路径，`thread/start.cwd` 实际收到默认工作区，接口没有报错。

修复方向：只有调用方没有指定目录时才使用默认值；明确指定而无法访问的路径应返回
可读错误，保留草稿，由用户选择新目录。不得默默扩大或改变工具操作的位置。

### 3. [P1] 引擎重启后保留了“已经加载会话”的错误假设

位置：`gateway/gw/codex.mjs:645`、`gateway/gw/codex.mjs:707`；进程退出清理见同文件第 611 行。

停止和进程退出都会清空 RPC、运行轮次与审批，但保留 `S.activeThread`。
下次发送只在 `!S.activeThread` 时执行 `thread/resume`，因此会直接向新进程发送
旧线程的 `turn/start`。引擎退出不会关闭网关 SSE，所以前端的 SSE 重连恢复也不能
保证覆盖此场景；用户可能必须手动重新打开聊天。

隔离网关状态复现确认没有发送 `thread/resume`。另使用两个真实引擎进程验证：
首进程完成并落盘的聊天，在第二个进程直接续聊返回 `thread not found`；显式恢复后完成正常。

修复方向：区分当前界面选中的聊天与本代引擎已加载的聊天，以 generation 维护加载清单，
发送前确保目标已恢复。恢复过程还需要保留按线程的去重锁与停止语义。

### 4. [P1] 当前提交没有通过完整发布流水线

证据：[GitHub Actions 43835495887](https://github.com/leemwood/coxdragon/actions/runs/43835495887)。

该提交的 Linux 网关全量测试结果：1591 项，1570 通过、10 失败、3 取消、8 跳过。
Java 检查和 APK 构建均被跳过。

这些结果不能直接理解为 10 个产品缺陷：日志同时包含旧界面的静态断言、隔离环境
缺少 `gzip`/运行夹具的问题，以及等待超时测试被取消。需要逐项辨别测试过时、测试环境
缺失和真实回归，不能只删除失败断言来变绿。

例如 `gateway/tests/a0610-f1-frontend.test.mjs:209` 仍匹配旧的脚本启动判断；
`gateway/tests/a0611-reconcile-fix.test.mjs:90` 在测试工具链里找不到 gzip；
`gateway/tests/card-timeout.test.mjs:13` 的等待 Promise 尚未解决时事件循环已经结束。

修复方向：先恢复完整 Linux 网关、Java 和签名构建检查，将目前单独运行的真实引擎
模拟服务验证与浏览器行为回归纳入可重复执行的发布检查。当前 38 项协议测试通过
和之前真机成功不能替代本次全量检查。

### 5. [P2] 停止后的线程加载回执仍能写回新状态

位置：`gateway/gw/codex.mjs:669`、`gateway/gw/codex.mjs:682`。

`startThread` 和 `resumeThread` 没有 `startTurn` 已有的 generation/RPC 校验，
等待这两个请求时也不计入 `codexActivity().busy`。停止引擎或切换连接后，旧回执
若在进程彻底退出前返回，仍可能恢复旧 `activeThread`、目录并广播线程事件。

隔离复现确认：请求在途时 busy 为 false，停止后让旧 `thread/start` 回执到达，
状态变成 server=false 但 activeThread 是旧线程。

修复方向：所有跨 await 的引擎状态写入统一核对 generation 和 RPC 实例；
将启动、恢复等在途操作纳入连接切换与维护互斥。不要只保护 `turn/start`。

### 6. [P2] 旧自动化仍在后台运行，但正常界面已经无法管理

位置：`gateway/gw/sched.mjs:383`、`gateway/gw/sched.mjs:554`、
`gateway/server.mjs:80`；前端入口重定向：`gateway/web/app/14-projects-sched.js:680`。

调度器仍加载旧任务并按时启动旧引擎队列，没有接入 Codex 执行，也没有迁移停用规则。
正常页面的 sched 入口已统一转到 Codex 侧栏。因此升级用户若留有启用的旧任务与可用
旧引擎配置，仍可能继续执行，而用户无法从正常界面查看、暂停或删除它们。
本项依据源码确认，未在用户手机上创建或触发任何任务。

修复方向：保留可见的迁移与暂停入口，明确显示任务属于哪个引擎；在接通 Codex 前
不能只隐藏调度页面。接入后用统一任务记录管理排队、取消、期限、失败、错过和结果。

### 7. [P2] 独立仓库与应用自动更新渠道仍不一致

位置：`android/java/cox/dragon/Updater.java:42`，下载与自动应用见第 837、841 行。

源码已推送至 `leemwood/coxdragon`，应用更新和工具包来源仍固定为
`greyoak111/coxdragon`。因此在新仓库发版不会自动成为这批安装的更新源；
自动更新仍按原仓库版本判断与下载。APK 签名校验仍存在，不代表任意包都能安装。

修复方向：分别声明应用更新源、工具包源和组件源，显示实际生效的渠道，允许用户
关闭自动更新；切换渠道时保留签名、哈希、兼容性校验与失败恢复。不要因新仓库暂无
工具包发布就一次替换所有源，也不要把私有仓库令牌写入 APK。

## 用户自由与自动化的后续方向

- 权限策略目前在新建和恢复时固定为 `untrusted`，界面仅展示。建议支持按项目保存的
  手动确认与无人值守策略、允许的工具、网络与目录范围；必须与安卓实际执行能力一致。
  对既有配置的临时 CLI 覆盖应有清楚的生效来源，避免用户修改文件后看似没有效果。
- 自动化采用持久化任务与状态转换，执行前绑定项目、连接和权限；同一计划时刻去重，
  可查询、暂停、取消，明确超时、重试次数、失败通知与错过计划的处理方式。
- 用户选项包括按任务改变模型与思考强度、已有任务继续补充指令、线程分页和归档恢复。
  目前全局模型偏好、50 条线程上限和仅本地存储的固定项，会限制长时间使用。
- 带候选答案的问题仍需允许用户自行输入；MCP 请求输入目前只有拒绝按钮，属于尚未
  接通的交互能力。应按真实协议提供操作，避免用仅显示说明的入口代替实际能力。

建议先处理前五项的执行状态、重复副作用与发布检查，再补可见的调度迁移和更新渠道，
随后扩大可配置权限与无人值守能力。

用户确认修复后，本轮实现了以下改动：

| 原问题 | 修复行为 |
| --- | --- |
